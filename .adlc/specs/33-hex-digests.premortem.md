# Premortem Report

> Generated by `premortem`. The model was told this project already failed and asked to write the postmortem.

## Failure Causes

| # | Cause | Earliest Signal | Prevention |
|---|-------|-----------------|------------|
| 1 | The 'SSE Chain Discontinuity' during the rolling deployment: Subscribed clients holding an old-format raw CBOR `_hex` in their local state received an SSE patch where `_fromHex` was the new digest. The reconciliation logic in the frontend, expecting an exact string match to verify the chain, failed the equality check and triggered an infinite 'hard-reload' loop for every active user as the gateway continuously served 'new' digests that never matched the 'old' local state. | Spike in 'Initial Sync' requests immediately following the canary deployment of `gateway/reads.ts`, which was misinterpreted as successful traffic redirection rather than a crash-loop. | Implement a 'Format Version' header or a transitional period where the gateway accepts either raw hex or digest in the `_fromHex` field during the 24-hour deployment window. |
| 2 | External audit-log verification failure: Third-party indexing services were ingesting the REST API and storing `_hex` as a proof-of-state. These services relied on `Buffer.from(node._hex, 'hex')` to re-parse the CBOR and verify signatures. Post-deployment, these indexers began attempting to parse 34-byte Blake3 hashes as CBOR, leading to malformed data errors and a total collapse of the external audit trail. | Webhook failure alerts from the 'Sentinel' indexing partner 15 minutes after the production deploy. | Strictly version the API or introduce a separate `_digest` field rather than repurposing `_hex` which had an established, implicit schema (CBOR-bytes-as-hex). |
| 3 | The 'Projection Leak' paradox: While the spec aimed to allow projections by hiding values, existing 'Smart Components' in the frontend were using `_hex` to compute local derived state (e.g., calculating the checksum of a specific sub-field to avoid a re-render). When `_hex` became a digest of the *entire* bucket, these components lost the ability to detect fine-grained changes, leading to 'stale UI' bugs where field updates didn't trigger re-renders because the bucket's aggregate digest hadn't changed in a way the component understood. | Customer reports of 'ghost updates' where data changed in the database but the UI remained static until a manual refresh. | A systematic audit of `n.hex` usage in the React layer, specifically looking for `useEffect` dependencies or `memo` comparators that use the hex string. |
| 4 | Memory-Address collision in the Browser Cache: The Apollo/Relay client used `_hex` as the unique `id` for normalization. Because `_hviewHex` (the hyperview) and `_hex` (the node) could occasionally represent the same underlying data structure, they now shared the exact same 68-char digest. This caused the cache to overwrite 'Node' objects with 'Hyperview' objects, leading to 'Type Mismatch' crashes when the UI tried to access node-specific fields on a cached hyperview. | Sentry logs showing 'undefined is not a function' in the rendering path for `resolvePinnedImpl` nodes. | Prefix the digests with a type-specific namespace (e.g., `node:1e20...` vs `view:1e20...`) to ensure global uniqueness across different object types in normalized caches. |
| 5 | Search Index Desynchronization: The server-side 'Derived Search' engine was using `rhizomatic.derived.from` (which stores `inputHex`) to track which documents needed re-indexing. While the spec claimed derivation was untouched, the 'read-time' change to `_hex` meant that the search results returned a digest, while the indexing-pipeline was still emitting raw hexes. Users could see search results but clicking them resulted in 404s because the UI tried to fetch the document using the digest as a key, which the legacy index didn't recognize. | 404 Error Rate spike in the `/rest/node/:hex` endpoint specifically coming from Search-referrals. | The search index must be re-keyed or updated to support digest-based lookups simultaneously with the gateway change. |
| 6 | Bandwidth 'Efficiency' Backfire: For small deltas (e.g., a single boolean toggle), the raw CBOR hex was ~12-20 characters. Replacing this with a mandatory 68-character Blake3 digest + prefix actually *increased* the metadata overhead for high-frequency, small-payload streams, resulting in a 300% increase in egress costs for the 'Live Dashboard' service which pushes thousands of tiny updates. | CloudWatch Billing alert for NAT Gateway Egress exceeding the monthly threshold within the first week of the month. | Perform a distribution analysis of current `_hex` lengths to determine if a fixed-width 68-char digest is actually an optimization for the median case. |

# §23.9 / §24.5 — the ocap half of the renderer sandbox (T172)

The worker bounds the HANG, the CRASH and the MEMORY. It does not bound REACH. This working spec
closes the reach half: a renderer's code runs with no filesystem, no network and no process
authority. It gets the node it is handed, and the pure computation of the language.

## User stories

1. **Myk hosts a stranger's app in a quarantine pool.** He blesses a peer's renderer into the pool.
   The renderer's code tries to read `~/.loam/operator.seed`. He sees the page refuse. He reads
   `envelopeReports()` and sees the render counted as faulted. The seed file is never opened.
2. **Myk publishes a renderer that reaches for the filesystem by accident.** `loam renderer publish`
   refuses at the door and names the import it will not allow. Nothing is appended to the ground.
3. **Myk publishes an ordinary renderer.** It draws its view. Nothing about the page changed. The
   render still costs what §23.9 says it costs.
4. **Myk blesses a peer's renderer whose module body loops forever.** The bless refuses inside a
   bounded time. The store keeps answering every other route while it does.
5. **Myk reads the store's own account of what it confines.** `esm.ts` and `render-worker.ts` state
   what is denied and what is not, precisely enough to act on. No sentence in either claims more
   than the code does.

## The promise

A renderer bundle has TWO call classes, and both must be confined:

- **the RENDER call** — `default(node)`, already inside `renderInWorker`'s Worker;
- **the MODULE BODY** — top-level code that runs when the bundle is imported. Today it runs TWICE:
  once on the SERVING THREAD (`importEsm`, from publish / bind / the T209 bless path) and again
  inside the render worker.

Measured at base 9a06d26, both classes reach everything: `node:fs` read and write, `process.env`,
`globalThis.require`, `fetch`, `node:child_process` (`execSync("id -u")` returned uid 1000), and a
module body evaluating on the serving thread with `isMainThread=true` and the server's own pid.

## The mechanism

**A CONFINED REALM, in the worker, before any bundle byte evaluates.** Two halves, and neither alone
is sufficient:

- **The module gate.** `module.registerHooks` refuses every specifier that is not the bundle's own
  `data:` URL — `node:fs`, `fs`, `file:`, `http:`, and any specifier a nested `data:` module names.
  The gate's own predicate is built from PRIMORDIALS CAPTURED BEFORE the bundle runs: a bundle that
  patches `String.prototype.startsWith` must not be able to make the gate's test lie.
- **The global scrub, by ALLOWLIST not denylist.** The allowlist is the bare-JS global set of a
  fresh `vm` context plus an explicit list of authority-free platform names. Everything else on the
  worker's `globalThis` is deleted — `process`, `fetch`, `WebSocket`, `navigator`, `require`,
  `module`, `BroadcastChannel`, `MessagePort` and any Node global a later version adds. The scrub
  VERIFIES itself and refuses the render if a denied name survived.

**Import-time moves off the serving thread.** `loadRenderer` no longer imports a bundle in-process.
It evaluates the module body in the same confined worker and reports only whether the default export
is a function. The serving thread learns a boolean and a content address; it never holds the
renderer's namespace.

## Acceptance criteria

1. A bundle whose module body reads a file through `node:fs` (static import) does not return the
   file's contents; the render refuses. Verified by `test/gateway/render-ocap.test.ts` ("a static
   node:fs import is refused").
2. A bundle whose module body reads a file through a dynamic `import("node:fs")` does not return the
   file's contents. The same fixture file IS readable by the test process, so the denial is the
   confinement and not an absent file. Verified by `test/gateway/render-ocap.test.ts` ("a dynamic
   node:fs import is refused, and the fixture really holds the secret").
3. A bundle that tries to WRITE a file leaves no file behind, and a control file the test wrote
   itself still exists. Verified by `test/gateway/render-ocap.test.ts` ("a renderer writes no
   file — and the bystander file survives").
4. A bundle that reads `process.env` cannot reach a secret the test put there. Verified by
   `test/gateway/render-ocap.test.ts` ("process is not in the renderer's realm").
5. A bundle that dials a real listening HTTP server gets no connection: the server records zero
   requests. Verified by `test/gateway/render-ocap.test.ts` ("a renderer opens no socket").
6. A bundle that imports `node:child_process` and runs a command leaves no evidence the command ran.
   Verified by `test/gateway/render-ocap.test.ts` ("node:child_process is refused").
7. A bundle that patches `String.prototype.startsWith` before importing `node:fs` is still refused —
   the module gate's predicate does not depend on a prototype the bundle can reach. Verified by
   `test/gateway/render-ocap.test.ts` ("the gate's own test cannot be made to lie").
8. A bundle whose MODULE BODY acts is confined too: publishing a renderer whose module body writes a
   file leaves no file, and no module body ever observes `isMainThread === true`. Verified by
   `test/gateway/render-ocap.test.ts` ("no module body runs on the serving thread").
9. A bundle whose module body never terminates does not wedge the serving thread: `publishRenderer`
   refuses inside a bounded time and the gateway still answers. Verified by
   `test/gateway/render-ocap.test.ts` ("an unterminating module body is bounded, not a wedge").
10. TWO-SIDED: an ordinary renderer still renders 200 with the right HTML, and a renderer using the
    pure ambient (`JSON`, `TextEncoder`, `URL`, `Buffer`) still renders. Verified by
    `test/gateway/render-ocap.test.ts` ("a well-behaved renderer is untouched").
11. TWO-SIDED: the confinement composes with the render budget rather than replacing it — every
    §23.9 and §24.5 rail stays green. Verified by `npx vitest run test/gateway/render-sandbox.test.ts
    test/gateway/render-spawn-clock.test.ts test/gateway/render-spawn-forwarding.test.ts
    test/gateway/render-cap.test.ts test/gateway/quarantine-envelope.test.ts
    test/gateway/quarantine-envelope-memory.test.ts test/gateway/quarantine-envelope-isolation.test.ts`.
12. A quarantine pool's renders are confined on the pool's own envelope: a pool-served bundle
    reaching for `node:fs` refuses and the pool's `faulted` counter moves. Verified by
    `test/gateway/render-ocap.test.ts` ("a pool render is confined and billed").
13. The disclosure in `src/gateway/esm.ts` states what remains, and what remains is TRUE: the loader
    is the resolver floor only, and no renderer bundle enters this process's ESM registry. Verified
    by `test/gateway/render-ocap.test.ts` ("the loader holds no renderer namespace").
14. The confinement is not free to delete: removing the scrub or the module gate turns rails 1–8
    red. Verified by `npx adlc hollow-test --target src/gateway/render-worker.ts --target
    src/gateway/renderers.ts --base 9a06d263c42442ee679a16e9352f7d0e36519890`.

## Named residuals — what this does NOT confine

- **§22 resolvers still evaluate on the serving thread.** A resolver is a derived function the
  resolution program calls synchronously; it cannot cross a thread boundary. Resolvers keep §22's
  in-process floor: operator-authored law in a governed store. `esm.ts` says exactly this.
- **CPU and wall clock inside the realm** are §23.9's and §24.5's, unchanged. This slice adds no
  bound and weakens none.
- **The browser peer cannot confine a renderer at all**, so it admits none. A bundle that cannot be
  confined is a bundle that does not mount.
